# DIRECT-PACK（试验版）

DIRECT-PACK 是一个用于二维矩形装箱的启发式求解原型。程序根据箱体底面尺寸、单箱载重、货物尺寸与重量、允许朝向和重心约束，在箱体底面生成不堆叠的摆放方案，并通过独立审计器重新验证结果。

> 当前定位为算法试验版，不是生产级调度软件。
>
> 搜索范围有限：未找到方案不代表问题无解；找到方案也不代表全局最优。

## 功能概述

- 支持矩形货物在箱体底面的二维排布；
- 支持 0° 和 90° 水平旋转；
- 检查越界、重叠、单箱载重和底面积利用率；
- 检查前后半箱重量差 FB 和横向重心偏移 LR；
- 使用 16 套确定性构造策略生成候选方案；
- 支持重心平移、局部修复和跨箱移动/交换；
- 通过独立审计器复算最终布局；
- 支持搜索状态保存、断点续算和完整性校验；
- 仅使用 Python 标准库，无第三方依赖。

## 当前不支持

- 不支持多层堆叠，所有货物的有效高度坐标必须为 0；
- 不支持任意角度旋转，只支持 0° 和 90°；
- 不求解三维空间中的三维旋转和层间布局；
- 不保证找到全局最优方案；
- 不保证在有限搜索预算内一定找到可行方案；
- 不自动决定业务上是否接受利用率不足的尾箱，结果会交由人工处理；
- `height_check=false` 时只表示“不检查单件高度”，不代表高度已经被验证。

## 环境要求

- Python 3.10 或更高版本；
- 不需要安装第三方库。

## 快速开始

在项目目录中运行：

```powershell
python -B runner.py demo.json demo-state.json
python -B check_result.py demo.json demo-state.json
```

示例箱底为 `2000 × 1000 mm`。两件 `1000 × 1000 mm`、各重 `100 kg` 的虚构包装恰好铺满一只箱体。

求解命令会输出类似内容：

```json
{
  "stop": "portfolio_complete_with_valid_plan",
  "completed": 20,
  "uncertain": 0,
  "target": 1,
  "valid": true,
  "boxes": 1,
  "business_digest": "<最终布局的 SHA-256>"
}
```

复核命令会输出类似内容：

```json
{
  "valid": true,
  "stage": "complete",
  "boxes": 1,
  "lower": 1,
  "business_digest": "<最终布局的 SHA-256>",
  "front_mean": "1",
  "overall_mean": "1",
  "height": "checked"
}
```

其中 `business_digest` 的具体值取决于最终布局。示例只用于演示程序行为，数值本身不代表实际装箱标准。

```text
direct-pack-main/

├── runner.py
├── solver.py
├── allocation.py
├── audit.py
├── check_result.py

```

| 文件 | 职责 |
|---|---|
| `runner.py` | 总调度、策略组合、尝试预算、状态保存和断点恢复 |
| `solver.py` | 输入规范化、箱数边界、自由空间、摆放策略、重心调整和局部修复 |
| `allocation.py` | 跨箱移动、交换和重新装箱 |
| `audit.py` | 独立复算布局约束和最终指标 |
| `check_result.py` | 加载已有结果并进行最终复核 |
| `demo.json` | 虚构演示输入 |

运行时的主要调用关系为：

```text
runner.py
├── solver.py
│   └── audit.py
├── allocation.py
│   └── solver.py
└── audit.py

check_result.py
├── runner.py
├── solver.py
└── audit.py
```

## 输入格式

输入文件为 JSON，结构示例如下：

```json
{
  "schema": "PACKING-TRIAL-1",
  "mode": "ordinary",
  "require_all": true,
  "parameters": {
    "L": 2000,
    "W": 1000,
    "H": 900,
    "payload": 500,
    "fb": 10,
    "lr": 10,
    "util": 0.8,
    "height_check": true
  },
  "items": [
    {
      "id": "ITEM-001",
      "l": 1000,
      "w": 500,
      "h": 400,
      "m": 100,
      "allowed": [0, 90]
    }
  ],
  "search": {
    "repair_rounds": 1,
    "repair_options": 2,
    "attempt_reserve": 2
  }
}
```

### 顶层字段

| 字段 | 含义 |
|---|---|
| `schema` | 固定为 `PACKING-TRIAL-1` |
| `mode` | 搜索模式：`ordinary` 或 `all_qualified` |
| `require_all` | 当前试验版固定为 `true`，要求处理全部货物 |
| `parameters` | 箱体和业务约束 |
| `items` | 待装箱货物列表 |
| `search` | 修复和搜索预算参数 |

### 箱体参数

| 字段 | 单位 | 含义 |
|---|---:|---|
| `L` | mm | 箱内长度 |
| `W` | mm | 箱内宽度 |
| `H` | mm | 箱内高度 |
| `payload` | kg | 单箱载重上限 |
| `fb` | kg | 前后半箱重量差上限 |
| `lr` | mm | 横向重心偏离中线的上限 |
| `util` | 比例 | 单箱底面积利用率门槛，取值大于 0 且不超过 1 |
| `height_check` | 布尔值 | 是否检查单件高度 |

### 货物字段

| 字段 | 单位 | 含义 |
|---|---:|---|
| `id` | - | 唯一货物标识，不能为空或重复 |
| `l` | mm | 货物长度 |
| `w` | mm | 货物宽度 |
| `h` | mm | 货物高度，仅用于单件高度检查 |
| `m` | kg | 货物重量 |
| `allowed` | - | 允许的水平朝向，只能使用 `0` 和 `90` |

重心计算假设单件包装的质量均匀分布。所有尺寸和重量必须大于 0。

### 搜索参数

| 字段 | 含义 |
|---|---|
| `repair_rounds` | 单箱局部修复的最大轮数 |
| `repair_options` | 单件重新插入时最多尝试的候选位置数 |
| `attempt_reserve` | 在基础尝试预算之外保留的余量 |

三个参数必须是非负整数，其中 `repair_options` 至少为 1。

## 两种搜索模式

| 模式 | 利用率规则 | 完成状态 |
|---|---|---|
| `ordinary` | 除最后一箱外，其余箱子必须达到 `util`；最后一箱允许利用率不足 | 存在尾箱时输出 `waiting_human_tail` |
| `all_qualified` | 所有箱子都必须达到 `util` | 所有箱体合格时为 `complete` |

无论采用哪种模式，每个箱子仍需满足边界、重叠、载重、FB、LR 和高度检查规则。

`waiting_human_tail` 表示算法已经找到布局，但最后一箱利用率不足，需要人工决定：

- 接受当前尾箱；
- 调整货物范围；
- 更换箱体规格；
- 继续寻找其他业务方案。

该状态不代表布局可以直接发运。

## 算法流程

```text
读取并校验 JSON
        ↓
计算箱数下界和上界
        ↓
从较小箱数开始搜索
        ↓
对每个目标箱数执行 16 套构造策略
        ↓
逐件贪心放置并维护自由矩形区域
        ↓
平移整箱货物以改善 FB 和 LR
        ↓
执行有限次局部修复
        ↓
独立审计构造结果
        ↓
选择最多 4 个候选方案进行跨箱优化
        ↓
再次审计并选出最佳有效方案
        ↓
保存状态和最终结果
```

### 16 套构造策略

16 套策略由三个维度组合而成：

```text
4 种货物排序 × 2 种空隙选择方式 × 2 种定位偏好
```

货物排序：

- `difficult`：难放的货物优先；
- `area`：底面积大的货物优先；
- `long`：长边大的货物优先；
- `heavy`：重量大的货物优先。

空隙选择：

- `short_side`：优先选择与空白区域贴合度高的位置；
- `waste`：优先选择剩余面积较少的位置。

定位偏好：

- `ends`：优先靠近箱体边缘；
- `center`：优先靠近箱体中心。

每套策略都从空箱开始独立构造方案。16 套方案构造完成后，程序从中选取最多 4 个完整方案进行跨箱修复。

该算法使用确定性的规则和精确分数计算，不包含随机数。同一输入、代码和搜索参数应产生相同结果。

## 重心与配平

程序按以下方式计算重心指标：

- FB：计算货物质量在箱体长度中线两侧的分布，并比较两侧重量差；
- LR：计算全部货物在箱体宽度方向上的合成质心，再计算其与中线的距离；
- 对跨越箱体中线的大件，按货物在左右两侧的实际长度比例分配质量。

求解器会先尝试整体平移货物来改善平衡，再通过同尺寸交换、单件重新插入和跨箱调整进行有限次修复。

## 独立审计

`audit.py` 不导入求解器，也不直接相信求解器给出的重量、面积、重心或利用率。

审计器会重新检查：

- 货物是否全部出现且只出现一次；
- 是否出现未知或重复 ID；
- 货物尺寸和朝向是否与输入一致；
- 是否越界；
- 是否发生矩形重叠；
- 是否存在非零高度坐标；
- 单箱载重是否超限；
- FB 和 LR 是否超限；
- 单件高度是否超限；
- 底面积利用率是否符合当前模式；
- 是否出现空箱。

`check_result.py` 会重新计算审计结果，并要求复算结果与状态文件中保存的审计结果完全一致。

## 结果状态

常见停止状态如下：

| 状态 | 含义 |
|---|---|
| `empty` | 输入中没有货物 |
| `proven_single_item_constraint` | 至少一件货物在尺寸、朝向、载重或高度上无法装入空箱 |
| `proven_bounds_conflict` | 计算出的箱数下界大于上界 |
| `portfolio_complete_with_valid_plan` | 已找到通过审计的方案 |
| `portfolio_exhausted_no_valid_plan` | 有限策略组合已耗尽，但没有找到有效方案 |
| `attempt_budget_exhausted` | 外层尝试预算已经用完 |

审计阶段还会使用：

| 阶段 | 含义 |
|---|---|
| `complete` | 所有箱体均满足规则 |
| `waiting_human_tail` | 布局有效，但存在需要人工决定的利用率不足尾箱 |
| `search_incomplete` | 没有找到通过审计的完整方案 |

## 状态文件与断点续算

状态文件保存：

- 规范化后的输入和搜索配置；
- 当前目标箱数、搜索阶段和策略索引；
- 已执行的尝试记录；
- 构造方案、修复事件和当前最佳结果；
- 程序文件的 SHA-256；
- 状态正文的 SHA-256。

续算时，输入、搜索配置或程序文件发生变化会拒绝沿用旧状态，以避免把不同版本的中间结果混在一起。

状态写入采用临时文件、强制落盘和原子替换。进程在单次尝试中途退出后，恢复时会将上次未完成的尝试标记为 `uncertain`。

同一输入、配置和程序可以继续使用原状态文件；新输入应使用新的状态文件名。

> 状态文件包含输入明细和最终布局，实际业务状态文件不应上传到公开仓库。

## 调试选项

`runner.py` 还提供两个开发调试参数：

```powershell
python -B runner.py demo.json demo-state.json --steps 3
python -B runner.py demo.json demo-state.json --crash
```

- `--steps N`：本次最多完成 N 次外层尝试；
- `--crash`：保存一个尚未完成的尝试后立即退出，用于测试续算和 `uncertain` 状态。

## 已知限制

- 矩形只能放在有限候选位置，不会遍历平面上的所有连续坐标；
- 每件货物优先选择当前顺序中的第一个可用位置，属于贪心构造；
- 跨箱优化只执行有限的移动、交换和重新装箱组合；
- 外层尝试预算不等于完整的计算复杂度上限；
- 大型输入可能产生较多自由矩形碎片和历史状态数据；
- 当前没有自动化测试、基准测试和持续集成配置；
- 现有示例仅覆盖简单方形货物恰好铺满一只箱体的场景。
